I’d apply range/algorithm changes selectively. Current guidance says ranges are good for correctness/composability only when codegen stays acceptable, with profiler/generated-code checks for hot loops and build-time checks for heavy generic/range additions.  Also avoid turning hot byte scanners into pretty pipelines unless measured, since the project guidance prioritizes measured hot paths, layout/copy/allocation reduction, then lower-level tuning. 

## Best opportunities

* **DONE: [P0] Reuse JSON member lookup table for DOM unknown-member rejection**

  * `src/json_codec.cxx:1433-1450`, `1573-1590`, `2392-2396`
  * Current: streaming decode already uses `find_json_member_lookup_entry<T>()` for large member counts, but DOM `unknown_members == reject` still does `object_members × static_members` tuple-fold scanning.
  * Change: use same hashed lookup path when `member_count > kJsonMemberLinearLookupLimit`.
  * Win: removes inconsistent O(N×M) path; likely real for large reflected/static DTOs.

* **[P0] Add reflected-member lookup for JSON reflection path**

  * `src/json_reflect.cxx:508-565`, `824-855`
  * Current: reflected streaming decode and DOM unknown-member rejection fold over all reflected members per key.
  * Change: generate constexpr reflected-member metadata table; lookup by key via same hash/probe pattern as static codec.
  * Win: improves reflection serde scaling; keeps C++26 reflection path from becoming “ergonomic but linear”.

* **DONE: [P0] Normalize client request-header overlay into one algorithm**

  * `src/net/client_wire.cxx:110-165`, `370-389`
  * Current: repeated scans across defaults/request headers: override lookup, prior default lookup, request-match-default lookup.
  * Change: build an `effective_request_headers(defaults, overrides)` helper/view; use it for both size estimation and serialization.
  * Win: avoids O(D×H + D² + H×D), reduces bug surface around duplicated default/override behavior.

* **[P1] Replace comma-token callback API with a zero-allocation token range**

  * Core parser: `src/net/http_types.cxx:368-385`
  * Users: `header_token_contains`, `response.cxx`, `etag.cxx`, `response_cache.cxx`, `compress.cxx`, `static_async.cxx`, `http_server_helpers.cxx`
  * Current: `for_each_comma_token(header, fn)` forces local mutable flags and callback state.
  * Change: expose `header_tokens_view(std::string_view)` yielding trimmed `string_view`s; use `std::ranges::any_of`, `count_if`, or explicit fold where early break matters.
  * Win: clearer HTTP header parsing, reusable algorithm vocabulary, still no allocation.

* **[P1] Parse route path patterns once**

  * `src/net/app_route_helpers.cxx:9-150`
  * `src/net/app.cxx:1118-1145`, `1464-1465`
  * `src/net/router_match.cxx:24-47`
  * Current: route validation, shape derivation, param-name collection, param-type collection, and router parse each rescan the path.
  * Change: create `route_segments()` / `route_params()` range or normalized `RoutePatternInfo`.
  * Win: fewer scans per route registration; one source of truth for wildcard/typed-param semantics.

* **[P1] Centralize top-level template-expression splitting**

  * `src/template_impl.cxx:316-388`, `625-668`, `1228-1343`, `1552-1574`
  * Current: multiple top-level token/char scans with slightly different escape/quote behavior.
  * Change: one `top_level_find/split` algorithm over static operator descriptors; use `std::ranges::find_if` over operator tables where clean.
  * Win: correctness consistency more than raw perf; avoids future parser drift.

* **DONE: [P1] Remove repeated `path.string()` allocations during template file sort**

  * `src/template_env.cxx:238-260`
  * Current: sort comparator calls `a.string() < b.string()`, allocating during comparisons.
  * Change: Linux path: sort by `p.native()` projection, e.g. `std::ranges::sort(files, std::less<>{}, [](auto const& p) -> auto const& { return p.native(); })`.
  * Win: easy allocation removal; good algorithm/ranges fit.

## Keep direct loops

* JSON parser/string scanner hot paths, socket I/O loops, CQ/SQ processing, work queues, and tiny DB param SoA copies should mostly stay explicit.
* Ranges there risk template/codegen noise, worse vectorization, or harder lifetime reasoning. The project guidance explicitly calls for checking iterator category, borrowing, lifetime, allocation behavior, and generated code before accepting range adaptors in hot paths. 

## Suggested order

1. JSON static/reflection member lookup reuse.
2. Client header overlay normalization.
3. HTTP token range.
4. Route pattern metadata/range.
5. Template top-level split centralization.
6. Template env sort allocation fix.
7. Lower-priority cleanup helpers above.
